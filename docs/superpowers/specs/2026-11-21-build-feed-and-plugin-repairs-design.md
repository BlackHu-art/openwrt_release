# 2026-11-21 构建来源与插件修复

## 目标与已确认方向

用户确认按失败分析修复批量固件构建，并逐个检查实际选用插件的上游修复，合入适用的改动。
11 月 7 日 18 个构建都在 squeezelite 来源检查停止；11 月 21 日还出现 Qt5 来源变化。
上传的 dump 日志另证实旧固件底座与当前 packages master 的 Rust 构建接口不配套。

## 方案与取舍

采用用户已确认的版本配套方案：保留已有显式固件提交，为其余配置记录确定提交，
按底座及 feed 分支固定完整提交，在获取和建立索引前使用该来源，获取后核对实际提交。
不同分支分别审查 Qt5/squeezelite 的真实配方，保留未知输入和部分修改拒绝能力。

整体升级所有固件底座会扩大设备、内核和配置迁移范围；只放宽文件哈希无法处理缺失 Rust
构建接口。因此这两种做法不作为本轮修复方式。外部插件按来源完整提交审查，必要修复
沿现有构建副本适配入口回移；原始受管输入与派生补丁保持分离。

## 边界

- 保留 18 个设备、LAN `10.0.0.1`、Argon/Aurora、既有插件选择和 fragments。
- 保留现有五个 VIKINGYFY IPQ60xx 的 `3fd1e27a511851b41cf082b067b60099e8e026c4` 固件提交。
- Passwall/CUPS 保持移除，京东云三个配置的 Docker 排除保持有效。
- 不把上游主题替换、Quickstart 替换或其他功能迁移混入必要修复。
- 上游修复记录来源、适用范围、已包含/合入/暂缓及原因；不可直接切换滚动 dev。
- 新的失败应定位实际来源，不隐藏索引错误，不将完整固件失败等同于测试通过。

## 实现结构

新增生产 feed 锁及一个独立 Python 适配器；由现有 feeds 阶段调用，保留 update.sh 的五参数接口。
适配器先验证底座身份、feed 名称/来源与锁，再将远端配置改为 OpenWrt 原生 `URL^commit`，
之后核对实际检出；未知底座或来源变化明确失败。配置预览和 CI 缓存身份应包含所用锁。

兼容和插件修复使用真实上游样本测试，覆盖首次应用、重复应用、未知输入、部分应用和失败传播。
CI 环境与 netfilter 只选择已确认适用的独立上游修复。

## 验证与交付

先运行现有回归记录基线；为失败版本和 feed 锁先写能失败的行为测试，再实现修复。
本机运行适用回归、来源校验、配置预览、文档链接和 diff 检查；Linux 必需检查由同一提交 CI 验证。
固件验证先选京东云 ImmortalWrt 和 LiBwrt 两个代表目标，使用构建流程而非发布流程。
记录主机跳过、Linux 检查、完整目标编译及尚未执行的实机验证边界。
